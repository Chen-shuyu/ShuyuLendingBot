# PLAN

## 目標

打造一個可 24 小時常駐、模組解耦、可觀測的 Bitfinex USD 放貸機器人。核心是把
[MikaLendingBot](../../MikaLendingBot) 的策略精華（FRR 底線、spread 分批、xDays 動態天期、
maxtolend 風控）以 Python 3 + `ccxt`（Bitfinex V2 API）重寫成純函式策略層，取代原本已停用的
Python 2 / Bitfinex V1 API 版本，並補上主迴圈狀態機、Rate Limit 重試、SQLite 收益記錄，
最終以 Podman 容器化常駐部署。

目前狀態：現有程式碼是「單次 dry-run 雛型」（跑一次即結束），本 milestone 規劃即是把它推進到
可正式上線常駐運作的版本。

### 第 0 期：收拾 D035 帶進來的尾巴（半天，擋在其他事情前面）

PR #31 改掉了定價基準，連帶讓三段既有邏輯失去意義，而**沒有任何測試蓋到**
——因為它們的失效條件是「候選價位高過訂單簿可見範圍」，在舊策略下不可能發生。
詳見 [TASKS.md](TASKS.md) 的盤查結果 A1～A3、B7～B9。

- [x] **A1 期望值的計算過程要進日誌** —— **2026-08-17 完成**。
  連帶修掉一個更嚴重的問題：**「不掛單」的理由是寫死的「可放貸金額不足」，
  而策略的六個出口裡有五個跟金額無關**——市場走弱時會出現
  「可放貸金額不足（目前 344.3 USD）」這種自相矛盾又指錯方向的日誌。
  三個策略的每個出口現在都講得出自己的理由。測試 512 → 517 項。
- **A2 重掛守門檻已退化成「永遠擋下往下調價」**。不是有人決定的，是連帶效果。
  **2026-08-18 拆成兩件事（D037）**：
  - [x] **A2-a —— 2026-08-20 完成（D039）**：越界時**棄權**而非偷偷否決，
    **而且會在日誌講出來**（棄權若是靜悄悄的，只是把「偷偷否決」換成「偷偷放行」）。
    兩個前置條件當天都成立：量測收到第一組「預估 vs 實際」、資金已借出所以
    放行成本為零。**當天的 30 輪現場資料把 D037 的推論變成量測**——
    兩個排隊金額 30/30 完全相同，而唯一放行的那一次是簿子變深造成的巧合。
  - **A2-b（移到第 2 期）**：新策略下的重掛政策，要在第 1 期的回測工具上跑過才定。
- [x] **A3 排隊位置日誌變成截斷值** —— **2026-08-20 完成（D039）**，與 A2-a 同批。
  越界時改口說「至少 N USD」並點出可見簿子的上限；要拿去比較的那條路直接不給數字。
  **下界不是沒有資訊，會騙人的是把它講成量測值的語氣。**
  （2026-08-19 現場：250 檔可見最高只有年化 9.04%，而我們掛 9.78%，
  日誌印的「前方 2,289,677 USD」就是截斷值。）
- [x] **閒置時間量測** —— **2026-08-19 完成（D038）**，原本掛在 A2-a 底下的那一半。
  每輪印出場上掛單已閒置多久、機會成本（USD）、與掛單當初預估的對照；
  新表 `offer_wait_forecasts` 存下掛單當下的預估。
  **同批修掉一個更根本的問題**：等待估計問錯了問題——問的是「命中間隔平均多長」，
  該問的是「我在任意時刻進場要等多久」，在陣發市場低估 3~4 倍。
- [x] **B7～B9 文件對齊** —— **B7（README）與 B8（ARCHITECTURE）2026-08-19 完成**；
  B9 是原始碼註解，當次指示不動程式，留在 TASKS。
- **C1 CI flaky**：自架 runner 下載 `actions/checkout` 被 GitHub CDN 限流（429），
  整合測試因此紅燈，但測試根本沒跑到。**看到紅燈卻不是真的壞掉，最消耗信任。**
  建議把整合測試改回 `ubuntu-latest`（只有 `deploy` 真的需要自架 runner）。
  **這一項要排在開啟分支保護之前**，否則這種 flaky 會把純文件 PR 也卡死。

**為什麼排最前面**：這三項都會在資金回來、機器人重新開始掛單的那一刻生效，
而且 A1 一旦缺席，後面所有「策略到底有沒有變好」的問題都答不出來。

### 第 1 期：量測基礎建設（這一期是為了讓後面的決策不再互相推翻）

**這是這次規劃的核心。** 沒有這一期，第 2 期只會變成第七個被推翻的決策。

- **M1　決策所需的資料落地**。每輪把當時的簿子摘要、成交摘要、K 線指標寫進 DB。
  目前 DB 有掛單、部位、收益、狀態四張表，
  **沒有任何一張存過市場長什麼樣**——所以每次分析都得重抓即時資料，
  用完就丟，而歷史再也回不去。
  **M1-a 市場快照（D042）與 M1-b 決策落地（D043）已完成並驗收通過**；
  **M1-c 重掛反事實落地（D046）是 2026-08-26 新增的第三塊**——
  每一輪有場上掛單時，把「保住 vs 改掛更高」兩條路的並排比較落下來。
  **只落資料、不改行為**，它產出的是 M2 要吃的反事實。
- **M2　回測工具**。餵歷史 K 線與 M1 落地的資料，對**任一策略**回答：
  「如果當時跑的是這個策略，會掛什麼價、多久成交、實質年化多少」。
  D035 的回測是手寫的一次性腳本，這一項是把它變成專案的常設能力。
  **驗收標準：拿它跑 `orderbook_depth`，要能重現出「賣在區間底部」這個已知結論。**
  重現不出來就是工具不對，不是策略對。
- **M3　成效量測**。「實際拿到的年化」對照「當時可達到的最佳」，兩個數字並列。
  沒有這一對數字，「策略變好了」永遠只是說法。目前唯一的成效證據是兩筆成交，
  其中一筆還是事故。

### 第 2 期：策略的剩餘工作（做在第 1 期的工具之上，不再靠即時快照）

- **A2-b　新策略下的重掛政策**（2026-08-18 從第 0 期移來，D037；
  **2026-08-26 由使用者的提案給出明確內容，見 D046**）。
  A2-a 讓守門檻改為棄權之後，「什麼時候該調價」就成了一個沒有主人的問題，
  而查證發現**往上調價從頭到尾就沒有判準**：只管往下的那道守門檻第一行
  就 `if candidate.rate >= live_rate: return None`，往上是「差超過 2% 直接重掛」。
  它需要的正是第 1 期的回測工具（M1-c 的反事實 ＋ M2）：
  **在什麼訊號下調價，長期期望值才最高。**
  ⚠ **該用的訊號是市場價位的走向，不是閒置時間**——「等太久」是成交比預期慢的
  證據，支持降價不支持漲價，混在一起會在市場走弱時去漲價。
  另要處理**棘輪**（連漲時一路追高、永遠不成交）。
  **不可以拿 2026-08-18 那一筆成交當依據**——當天守門檻根本沒被觸發（擋下重掛的是
  2% 利率容差），而且那是一個樣本。
- **P1-5 剩餘：天期維度**。`offer_period` 仍寫死 2 天。D030 的長期資料顯示
  30 天期毛利年化 10.47% vs 2 天期 6.47%，但溢價會大幅變動，
  **寫死任何天期都是錯的架構**。要一輪打三次 K 線端點（`p2`／`p7`／`p30`）各自估等待。
- **`ev_window_hours` 的敏感度**。目前 168 小時是拍板的：7 天窗最佳解年化 9.75%、
  30 天窗 10.50%，**我選了 7 天但沒有證據說它比較好**。
  這是 D036 三個問題裡唯一還沒過關的旋鈕——它對第 3 題
  （「過期時程式怎麼察覺？」）的答案仍然是「不會」。

### 第 3 期：收益要看得見（原優先級 2 的剩餘）

- **P2-2　`earnings_daily` 接上真實資料源**（Bitfinex ledger）。表和寫入介面 M3 就做好了，
  **從來沒有資料源**，到現在還是空的。
- **P2-4 剩餘：每日摘要**（利息數字依賴 P2-2）。
- **P4-1（B6）測試替身校正**——**排在 P2-2 之前**，ledger 是下一個回應解析的重災區，
  而 D027 記過的坑就是「測試看到的世界比真實世界乾淨」。

### 第 4 期：規模門檻與品質債（不擋前面）

- **P3-1／P3-2**：spread 百分位分佈、`maxtolend` 真實總曝險。
  **資金超過 500 USD 才有意義**——目前規模下年收益都是 +0.00 USD（D030 第六節）。
- **P4-2（B5）**：`餘額不足` 被 ccxt 歸類成 `AuthenticationError`，

### 這份規劃自己的驗收條件

如果三個月後回頭看，這份規劃有沒有用，看兩件事：

1. **有沒有再出現「決策 N 推翻決策 N-1」**。有的話，看那個決策是不是在
   第 1 期的工具上跑過——沒跑過就是紀律問題，跑過了還被推翻就是工具不夠。
2. **能不能回答「這個月實際年化多少、可達到的最佳是多少」**。答不出來就是 M3 沒做到位。
