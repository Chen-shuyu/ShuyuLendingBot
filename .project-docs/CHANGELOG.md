### Added（2026-08-24，分支 `feature/persist-pricing-decision`）
- **決策落地 M1-b**（D043）——**DB 第一次存下「我們怎麼想」**。
  在這批之前，`market_snapshots` 存著市場長怎樣，而「當時為什麼選那個價位」
  只存在該輪的記憶體裡
  - **新表 `pricing_decisions`，每「真的評估過一輪」一列**：選中的價位與它的等待分佈、
    對照組（等最短的那個候選）、候選集的**價位與實質年化兩排**、當時的窗長與最新那根
    K 的 `mts`、以及那個已知錯的 `hold_hours_assumed`（存的是**假設**不是事實——
    M2 換掉它之後，舊決策才比得了），`snapshot_id` 接回同一輪的快照
  - **寫入點緊貼 `_log_pricing_rationale()`**：兩者讀同一份 `last_evaluation`，
    於是**日誌那一行就是 DB 那一列的鄰行**。D041 擋著 M1-b 的理由是
    「DB 裡多一列假資料沒有鄰行會反駁」——**這個保護是靠位置接回來的，不是靠承諾**
  - **沒評估過的輪次一列都不寫**。08-24 那 130 輪（資金全借出、餘額守門檻擋在
    `choose_rate()` 之前）在這張表裡就該是 0 列——寫一列全是 NULL 的決策，
    會讓「這段期間評估過幾次」從 0 變成 130
  - **`last_window` 是新加的第三個「本輪狀態」，放進同一個重置點**。
    每多一個都是會跨輪殘留的成員（D041 已經有兩個），漏掉的那一個不會有人發現
  - **候選集只留兩排，成本是量出來的**：完整評估 17 KB、陣列的陣列 5.3 KB、
    兩排 **2.6 KB**。留 `effective` 是因為它就是排序依據——有它才答得出
    「為什麼是這個價位」（D3）。⚠ **其餘候選的等待分佈沒有存，而且重算不保證重現**
    （最新那根 K 事後被 UPSERT 過），表註解已標明不可以拿重算的東西冒充當時的決策
  - **整列實測 4,137 位元組**（寫 200 列再 VACUUM 量檔案增長）：一年約 50 MB，
    **最壞情況（每輪都評估）207 MB**——那是「市場一直很好、錢一直掛不出去」的日子，
    正好也是最想回頭看的日子
  - **不需要遷移腳本**：新表在啟動時由 `CREATE TABLE IF NOT EXISTS` 自動建好，
    與 D042／D038 走同一條路。已拿正式 DB 副本確認
  - 測試 618 → **650 項**（單元＋功能 624、整合 26）。對照實驗兩組都立刻變紅：

### Added（2026-08-23，分支 `feature/market-snapshot-landing`）
- **市場資料落地 M1-a**（D042）——**DB 第一次存下市場長什麼樣**。
  在這批之前有掛單、部位、收益、狀態、等待預估五張表，
  **沒有任何一張存過市場**，每次分析都得重抓即時資料、用完就丟
  - **`market_snapshots`（每輪一列）＋ `market_candles`（一根 K 一列）兩張表，
    不是 TASKS 原本寫的一張**。K 線每小時才換一根、巡檢 600 秒一輪，
    塞同一張表等於一天寫 34,560 列去講 24 根 K 的事。
    UPSERT 的**邊界含等號**是刻意的：最新那根還在成形中，少了等號每根 K 都會被
    凍結在剛出生那一刻的樣子，**而 `high` 正是這個策略唯一在意的欄位**（D035）
  - **這一批只存觀測，不存決策**。`core/market_snapshot.py` 的模組說明第一句就是
    「刻意不認識任何策略物件」——**界線要看得見，否則下次順手就越過去了**。
    M1-b（本輪選中的價位與候選集）等 D041 在正式環境驗收過才進來：
    日誌印錯還有鄰行可以拆穿，**DB 裡多一列假資料沒有鄰行會反駁**
  - **落地點在所有提早 `raise SkipCycleError` 的出口之前**——那些出口正好是
    「市場走弱、單子空掛」的輪次。這是 D038 那一課的重演，
    **差別在於日誌漏印還看得出來，DB 漏一列事後完全無感**。
    唯一例外：FRR 無效那一輪在抓資料前就離開，確實什麼都沒觀測到，
    **寫一列空的比不寫更糟**
  - **有損的地方都有欄位承認**（D039 從日誌延伸到資料表）：`book_truncated`、
    `trade_span_minutes`、沒觀測到的欄位留 NULL 而不是 0
    ——用 0 填會讓一段沒有資料的期間被讀成一段市場死掉的期間
  - **不需要遷移腳本**：`_create_schema()` 每次啟動都跑 `CREATE TABLE IF NOT EXISTS`，
    與 `offer_wait_forecasts`（D038）當初走同一條路。正式環境已確認自動建好

- **取消掛單後改為確認場上狀態，不再用餘額回推**（D031 的第二個缺口）。
  19:31 證明兩者會分岔：餘額沒回來不代表取消沒生效，也可能是那張單根本沒被取消。
  仍有單就整輪不重掛——**再掛一筆就是雙倍曝險**
- 日誌分出「候選價位」與「場上掛單」兩個排隊位置。原本只有前者，
  而 19:31 的誤讀正是把前者讀成後者
- `describe_queue()` 新增 `period` 參數：問「場上那張單排在哪」時天期要取自那張單，
  不能取自設定檔（分桶實驗一開始，同時掛 2 天與 30 天就是常態）

### Added（2026-08-16 夜間第三段）

### Changed（2026-08-16，分支 `feature/orderbook-pricing-and-fill-detection`）
- **定價基準改為訂單簿排隊位置**（TASKS.md P1-1、D030）。新增
  `strategies/orderbook_depth.py` 並設為預設（`strategy.mode`）。
  **根因**：舊策略掛 0.000272，而當時簿子頂端就是 0.000272——單子一直落在
  整個供給側的最後面，78 輪掛空。新演算法只有一句：在「前方排隊金額 ≤
  `target_queue_usd`」的前提下挑利率最高的一檔。實測會掛 0.000250（年化 9.12%）。
  **刻意不用 trades 百分位**：那會被爆發桶汙染，等於 FRR 落後問題換個來源重演
- **`minimum_rate` 語意改變**：從「算出來太低就拉高到這裡」改成
  「低於這裡就整輪不掛」。舊寫法會把價格拉到簿子外，掛一張永遠不會成交的單
- **不再每輪無條件取消重掛**：同利率下先掛先成交，每 600 秒重掛等於一天把自己
  送回隊伍末端 144 次。改為先查場上現況再比對，實質相同就什麼都不做
  （容差 `engine.rate_tolerance_pct`，預設 2%）
- **`spread_count` 由 3 改為 1**：344 USD 最多拆 2 筆，而第 2 筆會被乘到 0.000288、
  簿子頂端才 0.000270——一半的錢會變死單。**觸發條件正是「把資金全部投入」**
